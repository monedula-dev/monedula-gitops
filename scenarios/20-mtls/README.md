# Scenario 20 — mTLS client-cert auth

**Modes:** cli  
**Cluster profile:** auth-mtls

## What this teaches

Mutual TLS (mTLS) requires every connecting client to present a certificate
signed by the cluster's CA — not just encrypting the transport, but also
authenticating the client via its cert. This scenario verifies that the
Monedula CLI correctly loads the client certificate and private key from
files, negotiates the full mTLS handshake with the broker, and successfully
creates a topic.

The cluster profile (`scenarios/clusters/auth-mtls/`) provides a single-node
Kafka broker with `ssl.client.auth=required`. The dev client cert and key are
generated by `./certs/gen.sh` and live in `./certs/client.{crt,key}`. The
`cluster.yaml` references them via `file: certs/client.crt` (resolved relative
to `cluster.yaml`'s directory by the CLI's `FileEnvResolver`).

The cluster profile also sets `tls.caCert: { valueFrom: { file: certs/ca.crt } }`
so the CLI verifies the broker's (dev-CA-signed) server cert — the same
`caCert` field takes a `secretKeyRef` in operator mode.

## How to run

### CLI mode

```bash
monedula-gitops apply -f manifests/ \
  --cluster-config-file ../clusters/auth-mtls/cluster.yaml
```

## Expected outcome

The topic `mtls.demo` is created on the mTLS broker. The CLI exits 0 and its
output contains `mtls.demo`. A subsequent live-state check confirms the topic
exists on the broker.

## Cleanup

```bash
./cleanup.sh cli   # no-op (fresh broker per suite run)
```
