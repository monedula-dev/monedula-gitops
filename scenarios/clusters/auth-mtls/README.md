# Cluster Profile: auth-mtls

Single-node Kafka (KRaft) with **mutual TLS (mTLS)** — SSL client-certificate
authentication. The broker's CLIENT_HOST listener requires every connecting client
to present a certificate signed by the dev CA (`ssl.client.auth=required`).
There is no SASL layer; identity is established entirely through the client cert.

This profile is used by scenarios that require mutual TLS on the Kafka client
listener (e.g. `20-mtls`).

## Listener summary

| Listener    | Protocol | Auth               | Port |
| ----------- | -------- | ------------------ | ---- |
| CLIENT_HOST | SSL      | mTLS (client cert) | 9092 |
| INTERNAL    | PLAINTEXT| none (inter-broker) | 9094 |
| CONTROLLER  | PLAINTEXT| KRaft quorum       | 9093 |

## TLS certificates

Certificates live in `./certs/` and were generated by `./certs/gen.sh` (dev-only
self-signed CA + server cert + client cert). They are committed to the repository
so the test suite can run without requiring `openssl` at test time.

**DEV ONLY — never reuse these certs or the CA key in production.**

| File           | Purpose                                      |
| -------------- | -------------------------------------------- |
| `ca.crt`       | Dev CA certificate (trusted by broker + clients) |
| `ca.key`       | Dev CA private key (signs server + client certs) |
| `server.crt`   | Broker TLS certificate (SANs: localhost, kafka)  |
| `server.key`   | Broker TLS private key                       |
| `client.crt`   | Client certificate presented to the broker   |
| `client.key`   | Client private key                           |

The broker combines `server.crt` + `server.key` into a PEM keystore
(`/etc/kafka/secrets/server-keystore.pem`) at container startup via the
`entrypoint` wrapper. The CA cert (`ca.crt`) is used as the PEM truststore so
the broker can verify client certificates.

To regenerate (e.g. after expiry or key rotation):

```bash
bash scenarios/clusters/auth-mtls/certs/gen.sh
git add scenarios/clusters/auth-mtls/certs/
git commit -m "chore(certs): regenerate dev CA + server + client certs for auth-mtls"
```

## CLI mode (Docker Compose)

```bash
# From scenarios/clusters/auth-mtls/
docker compose -f compose.yaml up -d --wait

# Tear down
docker compose -f compose.yaml down -v
```

The broker uses a PEM keystore (Apache Kafka 3.x / cp-kafka 8.x
`ssl.keystore.type=PEM`). The compose entrypoint combines `certs/server.crt` +
`certs/server.key` into `/etc/kafka/secrets/server-keystore.pem` before the
broker starts.

The healthcheck probes the INTERNAL PLAINTEXT listener (`kafka:9094`) so no TLS
or client cert is required for the health probe itself.

### CLI-mode cluster.yaml

`cluster.yaml` authenticates with `auth.mechanism: mTLS` and supplies the client
cert + key from `./certs/`. It also trusts the dev CA via
`tls.caCert: { valueFrom: { file: certs/ca.crt } }`, so the CLI fully verifies
the broker's server certificate — no `insecureSkipVerify` needed. (In operator
mode the same CA is wired via a `secretKeyRef`; see `k8s-cluster.yaml`.)

```bash
monedula-gitops validate -f scenarios/20-mtls/manifests \
  --cluster-config-file scenarios/clusters/auth-mtls/cluster.yaml
```

## How mutual TLS works here

1. The broker presents `server.crt` (signed by dev CA) — the client verifies it
   against the dev CA (`tls.caCert`).
2. The broker requests a client certificate (`ssl.client.auth=required`).
3. The client presents `client.crt` (signed by dev CA) — the broker verifies it
   against its truststore (`ca.crt`).
4. If verification passes, the connection is established. No SASL exchange occurs.

## Opting into this profile

A scenario selects this profile in its `scenario.yaml`:

```yaml
cluster: auth-mtls
```

The test runner will start `scenarios/clusters/auth-mtls/compose.yaml` for CLI
mode before running the scenario.
