# Cluster Profile: auth-sasl-ssl

Single-node Kafka (KRaft) with **SASL_SSL / SCRAM-SHA-512** — SCRAM authentication
over TLS. Schema Registry is NOT included in this profile; scenarios that need
Schema Registry should use `shared-sasl` instead.

This profile is used by scenarios that require TLS on the Kafka client listener
(e.g. `04-sasl-ssl`).

## Listener summary

| Listener    | Protocol  | Auth               | Port |
| ----------- | --------- | ------------------ | ---- |
| CLIENT_HOST | SASL_SSL  | SCRAM-SHA-512 + TLS| 9092 |
| INTERNAL    | PLAINTEXT | none (inter-broker)| 9094 |
| CONTROLLER  | PLAINTEXT | KRaft quorum       | 9093 |

## TLS certificates

Certificates live in `./certs/` and were generated by `./certs/gen.sh` (dev-only
self-signed CA + server cert). They are committed to the repository so the test
suite can run without requiring `openssl` at test time.

**DEV ONLY — never reuse these certs or the CA key in production.**

The server cert covers SANs: `localhost`, `kafka`, `kafka.kafka.svc.cluster.local`.

To regenerate (e.g. after expiry or key rotation):

```bash
bash scenarios/clusters/auth-sasl-ssl/certs/gen.sh
git add scenarios/clusters/auth-sasl-ssl/certs/
git commit -m "chore(certs): regenerate dev CA + server cert for auth-sasl-ssl"
```

| Variable          | Value           | Role              |
| ----------------- | --------------- | ----------------- |
| `KAFKA_USERNAME`  | `admin`         | SCRAM super-user  |

## CLI mode (Docker Compose)

```bash
# From scenarios/clusters/auth-sasl-ssl/
docker compose -f compose.yaml up -d --wait

# Tear down
docker compose -f compose.yaml down -v
```

The broker uses a PEM keystore (Apache Kafka 3.x / cp-kafka 8.x `ssl.keystore.type=PEM`).
The compose entrypoint combines `certs/server.crt` + `certs/server.key` into
`/etc/kafka/secrets/server-keystore.pem` before the broker starts.

### CLI-mode TLS CA (cluster.yaml)

`cluster.yaml` trusts the dev CA via
`tls.caCert: { valueFrom: { file: certs/ca.crt } }` (resolved relative to the
cluster-config file), so the CLI fully verifies the broker's server certificate.

```bash
export KAFKA_USERNAME=admin
export KAFKA_PASSWORD=admin-secret
monedula-gitops validate -f scenarios/04-sasl-ssl/manifests \
  --cluster-config-file scenarios/clusters/auth-sasl-ssl/cluster.yaml
```

## k8s mode

### Prerequisites

Create the TLS Secrets (substitute real base64 values):

```bash
kubectl apply -f k8s/namespace.yaml

kubectl -n kafka create secret generic kafka-tls \
  --from-file=ca.crt=certs/ca.crt \
  --from-file=server.crt=certs/server.crt \
  --from-file=server.key=certs/server.key

kubectl -n kafka create secret generic kafka-ca \
  --from-file=ca.crt=certs/ca.crt
```

### Apply manifests

```bash
kubectl apply -f k8s/namespace.yaml
kubectl apply -f k8s/kafka-tls-secret.yaml   # or use kubectl create secret above
kubectl apply -f k8s/kafka.yaml
```

### k8s-mode TLS CA (cluster.k8s.yaml)

`cluster.k8s.yaml` wires the CA via `tls.caCert` with a `secretKeyRef` (a
Kubernetes Secret reference), which the operator's resolver supports. Use this
form when deploying the operator:

```bash
kubectl apply -f cluster.k8s.yaml
```

## Two cluster.yaml files

| File               | Mode      | Broker address                  | CA wiring (`tls.caCert`)                       |
| ------------------ | --------- | ------------------------------- | ---------------------------------------------- |
| `cluster.yaml`     | CLI (dev) | `localhost:9092`                | `valueFrom: { file: certs/ca.crt }`            |
| `cluster.k8s.yaml` | k8s/operator (reference) | `kafka.kafka.svc.cluster.local:9092` | `valueFrom.secretKeyRef: { name: kafka-ca, key: ca.crt }` |
| `k8s-cluster.yaml` | k8s/operator (e2e harness) | `host.docker.internal:9100`    | `valueFrom.secretKeyRef: { name: kafka-sasl-ssl, key: ca.crt }` |

`k8s-cluster.yaml` is the CR the e2e k8s harness applies (`setup_auth_profile auth-sasl-ssl`):
it targets the kind-facing `CLIENTKIND` listener (`host.docker.internal:9100`) of the host
compose broker. `cluster.k8s.yaml` is an in-cluster-DNS reference for a broker running inside
the cluster.

All three verify the broker against the same dev CA — the only difference is
where the CA PEM comes from (a file in CLI mode, a Kubernetes Secret in
operator mode). Scenarios reference whichever file matches their execution mode.

## Opting into this profile

A scenario selects this profile in its `scenario.yaml`:

```yaml
cluster: auth-sasl-ssl
```

The test runner will start `scenarios/clusters/auth-sasl-ssl/compose.yaml` for CLI
mode and apply `scenarios/clusters/auth-sasl-ssl/k8s/` for k8s mode before running
the scenario.
